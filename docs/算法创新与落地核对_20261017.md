## 可以重点展示的三项方法

### 一 带追问预算的确认式需求整理

输入“每天晚上都要我提醒，真的很累”，离线词语规则给出“实际帮忙”和“休息”两个候选，同时显示“提醒”“很累”这两段线索。系统不会替用户选定类别或勾选确认。

用户确认需要并选择继续安排后，从尚未填写的字段中选择一个问题：

`question = argmax(字段重要性 / 填写成本)`

当前字段为具体事情、负责人、日期、完成要求。对应重要性为 5、4、3、3，填写成本为 1、1、1、2。已填字段和已跳过字段不重复问。简单模式最多问一次、普通模式最多问两次；用户主动停止或不想安排则不再追问。

这些权重为工程设定，并非训练得到。它是确定性的字段优先级策略，不能称为基于语义概率的最优信息增益算法。可以在答辩中展示：同一句表达，在不同精力与已有字段情况下，问题顺序和停止位置不同。

共享草稿只投影用户在安排问题中主动填写的 title、owner、date、details；私人表达、模型解释、原文线索不复制进去。缺少字段保留空白，稍后由用户填写。需要保存与分享是分开的操作。

离线识别只是小词表与局部否定规则，不擅长隐喻、转述、复杂否定。没有线索时不猜测。原文线索可以帮助核对，但不能证明候选在语义上正确。

### 二 区分阶段和协调负担的保守推荐

候选活动先按时间过滤：简单模式上限为 `min(3, 用户可用分钟数)`，普通模式用用户选择的时长。反馈只使用与当前备孕/孕期/产后阶段相同的记录；缺少阶段的旧反馈仍保留，但不推测其阶段，也不用于新排序。

每类最多使用最近五条同阶段记录。每条有效记录的权重为：

`w = 2 ^ (-记录距今天数 / 30)`

对活动帮助、同类安排帮助、同类安排协调负担分别计算：

`m = Σ(w × 用户评价) / (2 + Σw)`

帮助评价：有帮助 1、一般 0、没有帮助/不适合 -1。不确定、缺失评价不进入对应维度的分子或分母。协调负担：没有 0、一点 0.5、较多 1，不确定不计入。未来时间或无效时间的记录不计入。分母中的 2 是中性先验质量，使一次记录不立即形成很强的偏好。

最终分值：

`S = 4×需要匹配 + 2×明确偏好 + m活动帮助 + m同类帮助 − λ×m协调负担`

普通模式 λ=1，简单模式 λ=2。相同分值优先较短活动，最后按 ID 稳定排序。界面显示各部分贡献、使用记录数、未使用记录数和历史开关；关闭历史后，只保留需要、偏好与时间。

这是一种可解释的场景化推荐策略原型。指数衰减、收缩估计和加权排序都已有研究基础，不是本项目发明。潜在贡献在于：孕产期阶段隔离、用户自主精力约束、帮助与协调负担的双目标，以及可纠正、可退出的组合机制。当前没有训练模型，也没有随机向用户推送不适合的活动去探索奖励。

### 三 可核验且不能自动分享的模型输出约束

接口只接受本次明确同意发送的一句话，不读取或打包整份记录。可接入兼容 Chat Completions 格式的服务，也可配置本机模型服务。

模型只能提出 `category + evidence` 候选，不能返回负责人、日期、完整安排或诊断。服务端和浏览器分别检查字段白名单、类别、重复项、长度及原文连续片段；失败显示错误并回到离线规则。即使格式检查通过，也必须由本人选择和确认，不能把格式合法误认为语义正确。

密钥只从启动服务的环境变量读取，不写入前端、备份或日志。页面展示配置的目标主机，并要求每次主动同意。未配置时没有“假 AI”；静态浏览器版仅使用离线算法，不将密钥塞进网页。

这是约束机制与工程实现，不能单独包装为新大模型或全新的算法。真实模型评测需等用户配置服务后，用带人工标注的虚构样例比较误解、越界补全与拒绝不当输出情况。

### 与原规则的受控对照

下表是人工构造的八项工程需求探针。它们针对本次新增目标设计，不是独立用户数据集，不是推荐准确率，不能据此宣称整体效果领先。原规则并未设计为满足新增目标。

| 工程要求 | 原加减分规则 | 本次规则 |
| --- | --- | --- |
| 其他阶段的反馈不沿用 | 不满足 | 满足 |
| 缺少阶段时不猜测 | 不满足 | 满足 |
| 单次历史反馈影响小于 1 | 不满足 | 满足 |
| 30 天前的反馈影响更小 | 不满足 | 满足 |
| 简单模式更重视协调负担 | 不满足 | 满足 |
| 不确定保持中性 | 满足 | 满足 |
| 关闭历史后不引用反馈 | 满足 | 满足 |
| 超过可用时间不推荐 | 满足 | 满足 |

追问对照：四个安排字段全部未知且全部跳过时，固定询问为四次；本策略简单模式一次、普通模式两次。两种模式最终仍有四个未知字段。少问问题同时意味着少收集信息，不能把这项结果写成完成率提高或填表总时间缩短。

复现命令（在项目根目录、有 Node 和 Python 的环境）：

```sh
node --test tests/need-planner.cjs tests/support-core.cjs online/tests/*.cjs
python3 -m unittest discover -s tests -v
node tests/evaluate_support.cjs
```

`tests/support-core.cjs` 验证保留的旧排序基线；`tests/need-planner.cjs` 验证新算法。基线只供研究对照，页面实际使用新排序。浏览器全流程脚本和本轮结果位于 `tmp/algorithm-upgrade`，使用独立虚构数据目录，没有修改个人正式记录。

## 后续如何证明算法值得采用

1. 固定一份预先标注的虚构表达集，包含明确需要、多重需要、否定、转述、未知时间、拒绝分享等类型；将调参样例与最终评测样例分开。
2. 配置模型后比较三组：直接生成、只做字段校验、字段校验加本人确认；记录擅自补全、误带私人信息、错误候选、用户修正量，而非只比模型语句流畅。
3. 对推荐进行消融：去阶段隔离、去衰减、去收缩、去负担项，检查各项贡献和失败案例。当前八项探针只是第一步。
4. 经适当同意和内容审核后做小规模可用性测试，比较操作数、完成时间、感知负担及能否看懂推荐理由。不能由工程测试推出预防或治疗产后抑郁的效果。
